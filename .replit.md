# Development Guidelines for FUB Lead Viewer

## Core Principles

### 1. Think First, Code Second
- **Always read relevant files before making changes**
- Understand the existing architecture and patterns
- Consider impact on other components
- Think through the problem completely before proposing solutions

### 2. Verify Before Executing
- **Check in before making any major changes**
- Present your plan and wait for approval
- Explain the approach clearly
- Allow for feedback and adjustments

### 3. Communicate Clearly
- **Provide high-level explanations at every step**
- Describe what changes were made and why
- Keep explanations concise but informative
- Focus on the "what" and "why", not just the "how"

### 4. Simplicity Above All
- **Make every change as simple as possible**
- Impact as little code as necessary
- Avoid massive or complex refactors
- One change should solve one problem
- Prefer small, incremental improvements
- Keep functions and components focused

### 5. Maintain Documentation
- **Keep architecture documentation up to date**
- Document how the app works inside and out
- Explain key design decisions
- Update docs when architecture changes

### 6. Never Speculate
- **Read files before answering questions about them**
- If user references a specific file, MUST read it first
- Investigate before making claims about the codebase
- Give grounded, hallucination-free answers
- Say "I don't know, let me check" rather than guessing

## Examples

### ✅ Good Approach
```
User: "How does the API route work?"
Assistant: "Let me read the API route file first..."
[Reads app/api/fub/[...path]/route.ts]
Assistant: "The API route works by..."
```

### ❌ Bad Approach
```
User: "How does the API route work?"
Assistant: "The API route probably uses fetch to..."
[Speculating without reading the file]
```

### ✅ Good Change
```
Problem: Button needs error handling
Solution: Add try-catch to one function
Impact: 5 lines changed in 1 file
```

### ❌ Bad Change
```
Problem: Button needs error handling
Solution: Refactor entire error system
Impact: 15 files changed, new architecture
```

## Workflow

1. **User makes request** → Read relevant files
2. **Understand the problem** → Think through solution
3. **Propose approach** → Get user approval for major changes
4. **Make changes** → Keep them simple and minimal
5. **Explain changes** → High-level summary of what was done
6. **Update docs** → Reflect architectural changes

## Remember

- Simple > Complex
- Read > Assume
- Ask > Guess
- Explain > Execute silently
- Document > Forget
